# 知識グラフ実験

この実験は、既存の Markdown を置き換えるものではない。人間が読む研究記録を `docs/` に残したまま、そこから**出典・年代・証拠状態つきの主張**を機械可読な形へ抜き出し、将来のリンク予測や時系列分析に使う。

現段階では HakkenOSS 全体を fork しない。まず `otowa-ankyoscape` 自体に小さな知識表現を持たせ、単純な三つ組・年代付き四つ組・Hakken THiGER 用 raw TSV へ再生成できるようにする。

抽出時の具体的な指示は [`prompts/extract-knowledge-graph.md`](../prompts/extract-knowledge-graph.md) に固定する。現在の抽出件数と KGE 分割結果は [`experiments/kge/STATUS.md`](../experiments/kge/STATUS.md) に記録する。HakkenOSS 側で実際に確認できた入力形式・THiGER 実装との境界は [`HakkenOSS接続.md`](HakkenOSS接続.md) に分離した。

## ディレクトリ

```text
otowa-ankyoscape/
├─ docs/                     # 人間向けの研究本文
├─ ontology/                 # 実体・関係・証拠状態の定義
│  ├─ entities.json
│  ├─ relations.json
│  └─ evidence.json
├─ data/
│  ├─ entities.jsonl         # 実体
│  ├─ sources.jsonl          # 出典
│  ├─ claims.jsonl           # 採用済みの主張・観察
│  └─ hypotheses.jsonl       # 未解決の仮説
├─ prompts/
│  └─ extract-knowledge-graph.md # ChatGPT 等での抽出規則
├─ scripts/
│  ├─ validate_graph.py             # 構造・参照整合性の検査
│  ├─ graph_stats.py                # 疎さ・relation 分布の診断
│  ├─ export_kge.py                 # 静的 KGE 用の三つ組 TSV
│  ├─ make_kge_split.py             # cold-start を避けた train/valid/test 分割
│  ├─ export_temporal_kge.py        # 年代付き四つ組 TSV
│  └─ export_hakken_thiger_raw.py   # Hakken THiGER raw schema
└─ experiments/kge/                 # リンク予測実験用
```

## 二層に分ける

### 1. 証拠つき主張層

歴史研究として保持すべき情報を落とさない。

```json
{
  "id": "claim:0007",
  "subject": "river:tsurumaki",
  "relation": "flows_to",
  "object": "place:nishi_aoyagi",
  "time": {"at": 1878},
  "evidence_status": "secondary_transcription",
  "sources": ["M1878"],
  "note": "原画像未確認"
}
```

### 2. 予測用の派生層

最初の ComplEx / DistMult 等の実験では、上の主張から必要なものだけを

```text
river:tsurumaki    flows_to    place:nishi_aoyagi
```

へ落とす。これは**派生データ**であり、元の証拠情報を上書きしない。

静的 KGE では年代違いで同一の三つ組になる claim を一つへ畳む。一方、時系列実験では

```text
subject    relation    object    year
```

を別の派生物として出し、年代を消さない。

## ChatGPT で抽出するときの規則

LLM は史料の代わりではなく、Markdown から候補構造を作る補助として使う。

1. `〔確認〕`、`〔観察〕`、`〔推定〕`、`〔二次転記〕`、`〔未確認〕` 等の区別を失わない。
2. **描かれていないことを「存在しない」に変換しない。**
3. 二次資料に引用された原史料を、原画像を見ていないのに `primary_source_checked=true` としない。
4. 不明な年代・緯度経度・流向を推測で埋めない。
5. 一文に複数の独立した事実がある場合は claim を分割する。
6. 「あり得る」「可能性がある」「未確認」は `claims.jsonl` の確定事実へ混ぜず、必要に応じて `hypotheses.jsonl` へ置く。
7. 主張には最低一つの `source` を結びつける。
8. 同じ地名でも時代・位置が異なる可能性がある場合は、新しい entity を切るか `ChannelSegment` を使う。
9. `River` と `ChannelSegment` を混同しない。たとえば「弦巻川」という河川概念と「1851年図に見える護国寺南西端の短い水路線」は必要なら別実体にする。
10. LLM が生成した JSON は、史料との照合前に自動的な「確認済み」へ昇格させない。

より厳密な再利用用規則は [`prompts/extract-knowledge-graph.md`](../prompts/extract-knowledge-graph.md) を参照する。

## 証拠状態

- `confirmed` — 根拠資料を確認し、現在の研究本文で確認事項として扱っている
- `observation` — 地図・写真等から本調査が直接読み取ったもの
- `inference` — 複数資料から導いた推定
- `secondary_transcription` — 原資料未確認の二次転記
- `source_location_only` — 書誌・所在のみ確認
- `pending` — 追加確認が必要
- `unconfirmed` — 未確認

ここでの `confirmed` は「永久に真である」という意味ではなく、**現在の出典管理上、確認事項として採用している**という意味で使う。

## 検証

Python 3 の標準ライブラリだけで動く。

```bash
python scripts/validate_graph.py
```

検査するのは主に以下。

- JSON / JSONL の構文
- entity / source / claim ID の重複
- entity type・relation・evidence status が ontology に存在するか
- claim の subject / object / source が実在するか
- hypothesis が参照する claim が実在するか
- `primary` と分類した資料が直接確認済みになっているか
- 二次転記が直接原資料確認済みとして記録されていないか

この検査は**歴史的真偽を判定しない**。構造が正しくても内容が誤っている可能性はある。

## 静的 KGE 用 TSV を作る

既定では `confirmed` と `observation` だけを出力する。

```bash
python scripts/export_kge.py
```

生成先：

```text
experiments/kge/triples.tsv
```

二次転記も含めて実験したい場合：

```bash
python scripts/export_kge.py --statuses confirmed,observation,secondary_transcription
```

最初の比較では、証拠状態ごとに学習データを変え、結果がどれだけ変化するかも確認する。

## train / validation / test に分ける

```bash
python scripts/make_kge_split.py
```

実体や relation が test にしか現れない cold-start を最初の小規模実験で誤って作らないよう、学習側に最低一つの出現を残せる辺だけを holdout する。

現在の保守的 export はまだ疎であり、要求した比率どおりに大量の辺を隠せない。この状態自体を「史料抽出をさらに増やす必要がある」という診断として扱う。実数は [`experiments/kge/STATUS.md`](../experiments/kge/STATUS.md) に残す。

## 年代付き TSV を作る

`time.at` が整数年として明記された保守的 claim だけを、四列で出力する。

```bash
python scripts/export_temporal_kge.py
```

生成先：

```text
experiments/kge/temporal/all.tsv
```

`period`、`start/end`、注記しかない claim について、都合のよい代表年を自動補完しない。時系列予測で年代を捏造しないためである。

## Hakken THiGER の raw schema を作る

HakkenOSS の `hakken-models` が dataset preparation で読む `edges.tsv` / `nodes_corrected.tsv` と同じ列構造へ変換する。

```bash
python scripts/export_hakken_thiger_raw.py
```

生成先：

```text
experiments/kge/hakken/raw/edges.tsv
experiments/kge/hakken/raw/nodes_corrected.tsv
```

HakkenOSS 側で確認した schema、THiGER 本体、THiGERLLM との違いは [`HakkenOSS接続.md`](HakkenOSS接続.md) を参照する。

## 最初のリンク予測実験

いきなり未解決問題へ答えを出させない。まず、確認済みの辺を意図的に隠して復元できるかを見る。

1. `claims.jsonl` を増やす。
2. 予測対象に適した関係だけ三つ組へ投影する。
3. train / validation / test に分割する。
4. test の既知辺をモデルから隠す。
5. ComplEx / DistMult 等で順位を付ける。
6. MRR、Hits@1、Hits@10 等で復元性能を見る。
7. その後に、水窪川・弦巻川の接続問題など本当に未解決の候補へ適用する。

データが少なすぎて既知辺すら復元できない場合は、HakkenOSS の大規模な仕組みを導入する前に、実体・関係の粒度や史料抽出方法を見直す。

## 「未来予測」は別評価にする

coverage-aware split は静的リンク予測の健全性を見るためのものなので、未来予測にはそのまま使わない。

Hakken 的な評価では、必ず

```text
過去年代だけで train
      ↓
それより後の期間を validation / test
```

とし、未来の史料から得た辺を学習側へ漏らさない。後年に初出する entity / relation は cold-start として別集計する。

## HakkenOSS との接続

当面は HakkenOSS を研究データの本体にしない。

```text
Markdown
  ↓
evidence-aware claims  ← 正本
  ├─→ 静的三つ組 TSV → Hakken TextKGDataset / KGE
  └─→ 年代付き四つ組 → THiGER raw schema → Hakken THiGER
```

という境界を置く。

調査の結果、HakkenOSS には時系列 GNN + Transformer の **THiGER 本体の学習・評価コードが公開されている**ことを確認した。一方、論文の `THiGERLLM` と同じ完全実装は現時点で確認できていない。したがって、「THiGER が OSS にある」ことと「論文の全構成がそのまま OSS で再現できる」ことは区別する。

モデルが未知リンクを高く評価しても、その出力は史実ではない。**次に確認すべき史料・地点の探索順位**として扱い、原資料で検証して初めて claim 側を更新する。
